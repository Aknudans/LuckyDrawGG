# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

LuckyDrawGG is a static, no-build toolset for running Magic: The Gathering Commander/EDH tournaments. It's plain HTML/CSS/JS pages with no bundler or package manager. The only external dependency is Firebase (Firestore + Authentication), loaded straight from its CDN as ES modules — Firestore syncs a tournament's live participant roster and pod results across devices (organizer's screen + players' phones), Authentication gates who can create a tournament. Everything else stays client-only.

- [index.html](index.html) — landing page linking to the tools.
- [modulo-armar-mazo.html](modulo-armar-mazo.html) — deck builder/validator ("Armar mazo"): parses a decklist (Moxfield export format, plain text, or a Moxfield link), detects the commander, and validates the 100-card singleton rule against the Scryfall API.
- [crear-torneo.html](crear-torneo.html) — tournament creator/setup ("Crear torneo"): gated behind Firebase Auth login/register (see below) — only an organizer with an account gets past the `authGate` panel. Once signed in, they set how many rounds the tournament has, open a waiting room (Firestore-backed), share its link/QR, watch participants join live, close registration to distribute players into pods of 3–5 (never 1v1 or bare pairs), and can re-shuffle before starting. This page's job ends at "▶️ Iniciar torneo": that sets the round-1 timer running and redirects to `torneo.html?code=...` — all further round-by-round control lives there.
- [torneo.html](torneo.html) — the organizer's live bracket/control screen for the whole tournament (all rounds), loaded by redirect from `crear-torneo.html` once the timer starts. Same auth gate pattern, but also checks `data.organizadorUid === currentUser.uid` — this screen is for the tournament's own organizer only, not just any logged-in account. See the dedicated section below.
- [unirse.html](unirse.html) — join page ("Unirme"): three-step, Kahoot-style flow. Step 1 validates the room code against Firestore (exists, and — for a first-time joiner — `estado === 'abierto'`) before showing anything else; only once that passes does step 2 reveal the name field and write the participant. Step 3 (`watchRoom`/`renderRoomState`) opens a live `onSnapshot` on the room doc: while `pods` isn't set yet it shows a waiting message; once pods exist it shows "Ronda X de Y", the participant's own pod for the *current* round (opponent names, tagged "Tú" on themselves) plus a live round timer (`renderTimerDisplay`, synced from `torneos/{code}.timer`); once `estado === 'finalizado'` it switches to a final-standings/podium view instead (`renderFinalStandings`). Because this is all driven by the same live listener, a participant's screen automatically jumps to their *new* pod each round with no action needed — the listener doesn't change, only the doc's `pods`/`rondaActual`/`estado` fields do. A returning participant (code already in `localStorage`) skips straight to step 3 even if the room is no longer `abierto` — that's how they check their pod/standings after registration closes. A code from the QR/link (`?code=`) auto-runs step 1 on load. This ordering is intentional — don't collapse it back into a single form.
- [firebase-config.js](firebase-config.js) — Firebase project config (`firebaseConfig` object), imported by `crear-torneo.html`, `torneo.html`, and `unirse.html`. Ships with placeholder values (`apiKey: "TU_API_KEY"`) — all three pages detect the placeholder and disable the room/join flow with an explicit warning instead of failing silently. A real project must be created in the Firebase console (see comments in the file) and its config pasted in; this is a manual, per-deployment step that can't be automated from here.
- [firestore.rules.txt](firestore.rules.txt) — Firestore security rules to paste into the Firebase console. Not deployed automatically (no Firebase CLI/build step in this repo) — copy-paste is the intended workflow.

There is no build system, package.json, linter, or test suite. To work on this, open the HTML files directly in a browser (or serve the directory with any static file server) — there's nothing to compile. Note that `crear-torneo.html` and `unirse.html` use `<script type="module">` for the Firebase imports, so opening them via `file://` may block ES module loading/CORS in some browsers — prefer serving over `http://localhost`.

- [iniciar-servidor.bat](iniciar-servidor.bat) — Windows launcher for manual testing on a real phone: auto-detects the machine's local IPv4 address, serves the repo on it at port 3001 via `npx serve`, prints the organizer/join/deck-builder URLs to enter on a phone (or scan via the in-app QR), and opens the organizer page automatically. Requires the phone to be on the same Wi-Fi/LAN — `localhost` URLs won't work from a phone.
- [serve.json](serve.json) — config for `npx serve`. `"cleanUrls": false` stops `serve`'s default 301-redirect from `/unirse.html?code=XXXX` to `/unirse`, which used to **silently drop the query string** and break the QR/link auto-fill flow. Disabling `cleanUrls` also disables `serve`'s built-in extensionless→`.html` resolution, so `"rewrites"` explicitly maps `/crear-torneo`, `/unirse`, `/modulo-armar-mazo` and `/index` back to their `.html` files (a stale browser-history entry or a hand-typed URL without `.html` would otherwise 404). Keep both blocks in sync if pages are renamed.

## Architecture notes

Each page is self-contained: styles in a `<style>` block, markup, and logic in a single inline `<script>` IIFE at the bottom. There is no shared JS/CSS file between pages — common visual language (dark theme, gold accent `#C9A227`/`#c9a227`, card-based panels) is duplicated per file rather than factored out. Keep that in mind when making cross-cutting visual changes: they need to be applied in each file individually.

### crear-torneo.html — auth gate, live waiting room + pod distribution

Firebase app/Firestore/Auth are initialized once at top level (`if (firebaseReady()) { ... }`), not lazily inside a button handler like the pre-auth version did — `onAuthStateChanged` has to be listening before the user does anything, since it's what decides whether `authGate` or `step1` is visible. `currentUser` is a module-level variable updated by that listener; every Firestore-writing handler downstream (`createRoomBtn`, `addManualBtn`, `closeRoomBtn`, `reshuffleBtn`) assumes `db`/`auth` are already set, since none of them can be reached while `step1` is hidden pre-login.

`authGate` has two tab-toggled forms (`showLoginTab`/`showRegisterTab`, `.tab-btn.active`). Login is plain `signInWithEmailAndPassword`. Register additionally requires picking an account type (`.account-type-btn`, `data-type="individual"|"tienda"`) before it'll submit — picking `tienda` reveals a required `direccion` field (`tiendaFields`). On success, `createUserWithEmailAndPassword` is immediately followed by `setDoc` on `usuarios/{uid}` with `{ tipo, email, direccion?, creado }`; if that second write ever needs to become resilient to partial failure (auth account created but profile doc missing), that's a known gap — currently a failure there just surfaces as a generic error with the auth account already existing. `traducirErrorAuth` maps Firebase Auth error codes to Spanish messages; extend that map rather than showing raw `err.code` if new auth flows are added. `logoutBtn` (`signOut`) also tears down the room UI state — unsubscribes any live listener, resets `roomCode`, and hides step 3/timer — since the next login could be a different organizer.

Joining a tournament (`unirse.html`) still requires no account at all — the gate only applies to *creating* one. This is enforced both in the UI (step1 hidden pre-login) and in [firestore.rules.txt](firestore.rules.txt) (`torneos` `create`/`update` require `request.auth != null` and ownership via `organizadorUid`; `participantes` `create` still has no auth requirement).

Data model in Firestore: `torneos/{code}` (fields `estado`: `'abierto'|'cerrado'`, `creado`, `organizadorUid`) with a `participantes` subcollection (fields `nombre`, `unidoEn`). `code` is a random 5-char string generated client-side (`generateCode`), not a Firestore auto-ID — it's what goes in the shareable link/QR (`unirse.html?code=...`) and what players type in manually if they don't scan.

Flow: `createRoomBtn` creates the room doc and opens an `onSnapshot` listener (ordered by `unidoEn`) that live-renders the roster and enables "cerrar inscripciones" once there are ≥3 names. `unirse.html` looks up the room doc by code, checks `estado === 'abierto'`, and `addDoc`s a participant — it never reads or writes anything else, and can't edit/remove entries (see [firestore.rules.txt](firestore.rules.txt)). The organizer can also add walk-in names manually into the same subcollection (`addManualBtn`) so mixed remote/in-person signup merges into one list. `localStorage` on the join page (`ld_joined_{code}`) just prevents a participant from double-submitting on refresh — it's not auth.

Closing registration (`closeRoomBtn`) snapshots the current roster into `lastRosterNames`, flips `estado` to `'cerrado'` (so late joiners get rejected by `unirse.html` and by the security rules), and unsubscribes the listener — the pod step no longer reacts to Firestore.

All three Firestore-writing handlers (`createRoomBtn`, `addManualBtn`, `closeRoomBtn`) wrap their `await` calls in try/catch, disable-then-re-enable their trigger button, and surface failures via `countWarning`. This isn't optional error-handling boilerplate — without it, a transient Firestore hiccup (the WebChannel `Listen`/`Write` streams do occasionally error and reconnect, confirmed via the console during testing) leaves the button permanently disabled with no code/roster ever rendered and zero feedback, which reads as "the app is broken" rather than "retry". Keep this pattern if you add more Firestore calls here.

`distributePods(n)` chooses the number of pods by minimizing `|n/pods - 4|` over the valid range `[ceil(n/5), floor(n/3)]`, then spreads the remainder round-robin so pod sizes differ by at most 1. This is what guarantees pods of 3–5 with no leftover 1v1s/pairs. `lastRosterNames` is shuffled and redistributed across those pod *sizes* (`shuffle` + `renderResultPods`), both on close and on "volver a sortear" (`buildPodsArray`).

Pod assignments are also written to Firestore (`torneos/{code}.pods`) on both close and reshuffle, so participants can see their own pod from `unirse.html` in real time — **not just render locally on the organizer's screen**. `pods` is `{ jugadores: string[], ganadores?: string[] }[]`, i.e. an array of maps each holding plain name arrays — **not** `string[][]`: Firestore rejects arrays nested directly inside arrays, which is why each pod is wrapped in a map. `unirse.html`/`torneo.html` match by exact name string against this same collection (no participant IDs), which is a known limitation shared with the rest of the no-login design: duplicate names in one room are ambiguous.

`crear-torneo.html` no longer owns the round timer's day-to-day controls — it only sets the round-1 timer running (`totalSeconds`/`endsAtMillis`/`running: true`) as part of "▶️ Iniciar torneo" and immediately navigates to `torneo.html`. All later Aplicar/Iniciar/Pausar/Reiniciar interaction, for every round, happens on `torneo.html`.

### torneo.html — multi-round bracket, results, and standings (organizer only)

This is where the actual tournament happens after setup. It takes `?code=` from the URL and opens a single `onSnapshot` on `torneos/{code}` — the same pattern as `unirse.html`'s `watchRoom`, but for the organizer: every field on the doc (`pods`, `puntos`, `rondaActual`, `timer`, `estado`) drives a full `renderRoom(data)` re-render, so the UI never has separate/stale local state to reconcile. Before attaching that listener it double-checks `data.organizadorUid === currentUser.uid` on the first snapshot and bails to a "no tienes permiso" panel (`showNotReady`) if it doesn't match — `torneos.read` is public in Firestore (required for `unirse.html`), so this ownership check is a UI-level gate, not a server-enforced one; only *writes* are actually protected, by the `update` rule's `organizadorUid` check in [firestore.rules.txt](firestore.rules.txt).

**Declaring a pod's result** (`toggleGanador(podIndex, nombre)`): clicking a player's "Marcar ganador" button toggles that name in/out of that pod's `ganadores` array — there is no separate "empate" control. Marking exactly one person is a clean win; marking two or more is how a tied/timed-out result with several players still alive gets recorded. Every toggle rewrites the *entire* `pods` array (Firestore has no partial-array-element update, so every write here is a full-array replace built from the last-known `currentPods`) and pushes it with `updateDoc`. Critically, `toggleGanador` mutates the module-level `currentPods` (and calls `renderPodsGrid()`) **synchronously, before** the `await updateDoc(...)` — it does not wait for the round-trip through Firestore's `onSnapshot` to update local state first. This was a real bug caught in testing: declaring results for two different pods in quick succession (two clicks close together) both read the same stale `currentPods` snapshot before either write's confirmation came back, so the second `updateDoc` clobbered the first pod's result. Updating local state optimistically before persisting closes that window — keep this pattern for any future per-pod mutation here. There's a per-pod "Deshacer resultado" button (clears `ganadores` back to `[]`) since this is a single click with no confirmation step — it needs to be cheap to undo a misclick. "Cerrar ronda y continuar" stays disabled until `currentPods.every(p => p.ganadores?.length > 0)`.

**Auto-resolving pods when the clock hits zero** (`resolverRondaPorVida`, wired into `renderTimerTick`): the organizer doesn't have to manually visit every pod and ask who won. When `timerRemaining() <= 0` on the `running: false → hits zero` edge (guarded by `timerExpiredHandled`, a module-level flag reset whenever a fresh countdown is applied/started/reset — see `applyTimerBtn`/`startPauseBtn`/`resetTimerBtn`, so this only fires once per expiry, not every second while the clock sits negative), it reads the live `vidas/r{ronda}_p{i}` doc for every pod that doesn't *already* have a manually-declared `ganadores` (those are left untouched — a pod finished early by hand is never overwritten) and sets `ganadores` to whichever players in that pod currently have `vida > 0`. This reuses the exact same scoring rule as manual declaration for free: one survivor is a clean win (3 points), several survivors split a point each, because "who's still alive when time runs out" *is* the same shape as "who did the organizer mark by hand." If nobody has positive life (a rare simultaneous-KO edge case), it falls back to marking the whole pod as `ganadores` rather than leaving the round permanently stuck with an unresolvable pod. This only *fills in* the result — "Cerrar ronda y continuar" is still a manual click, so the organizer gets to glance over the auto-picked winners (and override any of them, same as a manual declaration) before points actually lock in and the round advances.

**Scoring**: a pod with exactly 1 name in `ganadores` gives that player 3 points; a pod with 2+ names (several players still at the table when time ran out) splits 1 point to *each* of them, not among them — so a 2-survivor timeout gives both players 1 point each, not 0.5. This mirrors the simplified version of the common LGS/store Commander-tournament scoring pattern (win = most points, a timeout gives everyone left a token point) rather than a more granular kill-point system.

**Advancing rounds** (in `closeRoundBtn`'s handler): points from the just-closed round are folded into the cumulative `puntos` map, the round (with its final `pods`) is appended to `rondasCompletadas` for the record, and — if `rondaActual < rondasTotales` — the *next* round's pods are built by sorting every participant's name by cumulative points (ties broken by a pre-sort `shuffle()`, not alphabetically, so ties aren't systematically biased) and chunking that sorted list top-down into fresh pods via `distributePods`/`buildPodsArray`. This is **power pairing** (pods built top-down from current standings), not full Swiss (which additionally avoids repeat opponent pairings via backtracking) — power pairing is simpler to implement correctly and is an accepted alternative per how tools like TopDeck.gg describe Commander tournament pairing. `timer` is reset to `null` for the new round (so it shows "Configura los minutos y presiona Iniciar" instead of a stale time) — the organizer re-applies/starts it per round from this same screen. If it *was* the last round instead, `estado` flips to `'finalizado'` and there's no next-round pod generation — `renderStandings`/`unirse.html`'s `renderFinalStandings` both read top-of-`puntos` as the champion.

### Round timer sync

`torneos/{code}.timer` (shape `{ totalSeconds, remainingSeconds, endsAtMillis, running }`, or `null` between rounds): rather than decrementing a counter every second and writing that to Firestore continuously, the timer stores an *anchor* — `endsAtMillis`, the epoch-ms instant it hits zero — and every device (organizer and each participant independently) recomputes `remaining` locally every second as `endsAtMillis - Date.now()` while `running`, or reads `remainingSeconds` directly while paused. This is why `persistTimer()`/`timerRemaining()` in `torneo.html` only write on the four control actions (Aplicar/Iniciar/Pausar/Reiniciar) — never on a tick — and why `unirse.html`'s `renderTimerDisplay()` runs off a local `setInterval` reading the last-received `lastTimerState`, not a new Firestore read each second. This design means the countdown doesn't drift or stall if a tab is backgrounded/throttled (a plain `setInterval` decrement would), and it keeps Firestore writes rare. It relies on each device's system clock being roughly correct — no server-clock reconciliation is done, which is an accepted tradeoff for a casual round timer, not a competition-grade one. The timer only appears in `unirse.html` once `data.timer` is non-null on the room doc — a participant never sees a phantom default timer, including in the gap between rounds where it's reset to `null`.

### Shared life counter (`torneos/{code}/vidas/{rN_pM}`)

Every pod, every round, gets its own doc in this subcollection — key format `r{ronda}_p{podIndex}`, e.g. `r1_p0`. It holds a `jugadores` map keyed by player name, each value `{ vida, veneno, energia, experiencia, radiacion, tickets, danoComandante: { [oponente]: number } }` (life defaults to 40, everything else to 0). This is deliberately the complete set of official Magic *player*-level counters — poison, energy, experience, rad(iation), and ticket (introduced in *Unfinity*) — not creature/permanent counters, and not a partial/placeholder list. **Any participant in that pod can read and adjust any other player's counters from their own phone** — this isn't a per-device "your counter" widget, it's one shared game state everyone in the pod is looking at and editing together, so if whoever was tracking life on their phone has it die mid-game, anyone else at the table already has the same numbers in front of them and can keep going without re-entering anything.

**Who creates the doc, and when**: never lazily/client-side on first touch — that would race two phones both trying to initialize the same doc at once and risk one clobbering the other's already-adjusted values back to defaults. Instead the *organizer* creates it deterministically, with `buildVidasDefaults`/`crearVidasParaRonda`, at the exact same moment they generate that round's `pods`: in `crear-torneo.html`'s `closeRoomBtn` and `reshuffleBtn` (round 1), and in `torneo.html`'s `closeRoundBtn` (every subsequent round). By the time any participant's screen can possibly reference a given `podKey`, the doc for it already exists with sane defaults for every player in that pod.

**Why increments, not read-modify-write**: `unirse.html`'s counter buttons (`ajustarContador`/`ajustarDanoComandante`) write with Firestore's `increment(delta)` field transform via a dotted field path (e.g. `jugadores.Ana.vida`), not by reading the current value and writing back current+delta. This was deliberate and tested: with plain read-then-write, two phones tapping "-1" on the same counter near-simultaneously would both read the same starting value and one write would clobber the other, silently losing a decrement — the same class of bug already hit and fixed once for `torneo.html`'s pod-result declarations. `increment()` is resolved atomically server-side regardless of write order, so concurrent taps from different devices always accumulate correctly. Verified in testing: 10 rapid `-1` taps split across two separate tabs/devices landed on exactly `-10`, no drops. As with pod results, the UI still updates `currentVidas` optimistically and re-renders *before* the `await updateDoc(...)` resolves, purely for instant visual feedback — the correctness guarantee comes from `increment()` on the server, not from the local optimistic write.

Player names are used as literal dotted-path segments (`jugadores.${nombre}.vida`) without escaping — a name containing a literal `.` would target the wrong nested field. This is accepted as the same class of limitation already documented for duplicate names elsewhere (no login, no participant IDs, names are the only identity) rather than solved with `FieldPath` array-segment addressing, to avoid a new import/pattern not used anywhere else in the codebase.

Each seat's counter markup (`renderSeatContent` in `unirse.html`) always shows life with big ±1/±5 buttons; poison/energy/experience/radiation/tickets/commander-damage are behind a per-player "Más ▾" toggle (`contadoresExpandidos`, a `Set` of names, module-level so it survives re-renders from live snapshot updates) to keep 3–5 player cards from overwhelming a phone screen. Poison shows red at ≥10, commander damage red at ≥21 (the real lethal thresholds), matching the same "danger" visual language used elsewhere (`.timer-display.danger`, low-life). A per-player "Reiniciar contadores" button resets just that one player back to defaults via `setDoc(..., {merge:true})` — useful for a scooped/restarted game without leaving the pod's other players' counters untouched.

The security rule for this subcollection is deliberately wide open (`allow read, write: if true`) — no auth, no shape validation — at the same trust level as joining as a participant: the room code is the only access control. Rules can't easily validate a map whose keys are arbitrary participant names, and the whole point of this feature is that no player needs an account to touch it.

**Dedicated full-screen life view, and "Mi celular" vs "Modo mesa"**: the counters don't just sit inline in the normal pod view — `unirse.html` has a second full-viewport overlay (`#vidaScreen`, `position: fixed; inset: 0`) that swaps places with `.panel` (`mostrarVidaScreen`/`ocultarVidaScreen` toggle `.hidden`/`.show`). The swap happens **automatically** the moment the round timer starts running: `renderRoomState` tracks `lastTimerRunningFlag` and calls `mostrarVidaScreen()` only on the `false → true` edge of `data.timer.running`, not on every snapshot — otherwise every organizer pause/resume during a round would yank participants back to this screen even if they'd deliberately navigated back to "Ver ronda" to check standings. Each pod is laid out as two flex rows (`repartirAsientos`: 4 players → 2-and-2, 3 → 1-and-2, 5 → 2-and-3), which is what actually delivers the "2 facing 2" layout requested — seat order comes straight from the pod's `jugadores` array order, so it's identical and stable across every device looking at the same pod.

There are two display modes, toggled per-device by `toggleMesaBtn` (this is a **local UI preference, not synced** — the underlying counter data is shared via Firestore regardless of which mode each phone is showing):
- **"Mi celular"** (default): each player looks at their own phone normally, no rotation — the 2-and-2 grouping exists purely so it's faster to visually scan than a flat list, not to solve a shared-screen problem.
- **"Modo mesa"**: for the case where one phone gets laid flat in the middle of the table instead of everyone holding their own — the top row's seats get `transform: rotate(180deg)` (via a `.rotated` class in `renderSeat`) so whoever's sitting across the table reads their number upright without physically rotating the device. This mirrors the standard convention used by dedicated life-counter apps (e.g. life-counter.de's Commander layout), adapted here for a per-player-phone architecture rather than a single always-shared screen. Buttons inside a rotated seat still work normally on tap — CSS `transform` doesn't affect hit-testing, confirmed in testing.

### modulo-armar-mazo.html — decklist parsing and validation

State machine driven by a `state` object (`tab`, `commanderCards`, `deckCards`, `resolved`, `manualCommanderKeys`) inside the IIFE.

- Two text parsers: `parseMoxfieldFormat` (expects `Commander` / `Deck` section headers, exported directly from Moxfield) and `parsePlaintextFormat` (no headers; assumes the *last* line is the commander). Both funnel through `parseCardLine`, which extracts qty/name/set/collector-number via regex.
- Card validation calls the public Scryfall collection endpoint (`POST https://api.scryfall.com/cards/collection`) in batches of 75 to resolve card names to real cards (art, type line, legality-shaped checks). No API key needed; failures are treated as "unresolved" rather than fatal.
- The "Enlace de Moxfield" tab currently cannot succeed: Moxfield's API is not authorized for this app, so `handleLinkImport` deliberately throws after the fetch and shows a fallback prompting the user to paste text instead. Don't try to "fix" this without first getting real Moxfield API access — the failure is expected/documented behavior, not a bug.
- Commander detection is automatic (first/last card depending on parser) but overridable: `manualCommanderKeys` lets the user star any card in the full list as the commander instead.

## Language

All UI copy, labels, hint text, comments, and communication with the user must be written in **neutral (Latin American) Spanish** — never Argentine or any other regional dialect. In practice:

- Use `tú` conjugations for the second person singular (`tienes`, `quieres`, `elige`, `ingresa`), never `vos`/voseo (`tenés`, `querés`, `elegí`, `ingresá`).
- Avoid Argentine-specific vocabulary and slang (e.g. `acá` → `aquí`, `link` → `enlace`, `celular` is fine as it's widely understood, but region-specific idioms should be avoided in favor of terms understood across all Spanish-speaking countries).
- When adding or editing any user-facing string in these HTML files (or writing chat responses to the user), review it against this rule before finalizing — it's easy to slip back into voseo out of habit.
