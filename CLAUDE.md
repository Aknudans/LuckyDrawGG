# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

LuckyDrawGG is a static, no-build toolset for running Magic: The Gathering Commander/EDH tournaments. It's plain HTML/CSS/JS pages with no bundler or package manager. The only external dependency is Firebase (Firestore + Authentication), loaded straight from its CDN as ES modules — Firestore syncs a tournament's live participant roster and pod results across devices (organizer's screen + players' phones), Authentication gates who can create a tournament. Everything else stays client-only.

- [index.html](index.html) — landing page linking to the tools.
- [modulo-armar-mazo.html](modulo-armar-mazo.html) — deck builder/validator ("Armar mazo"): parses a decklist (Moxfield export format, plain text, or a Moxfield link), detects the commander, and validates the 100-card singleton rule against the Scryfall API.
- [crear-torneo.html](crear-torneo.html) — tournament creator ("Crear torneo"): gated behind Firebase Auth login/register (see below) — only an organizer with an account gets past the `authGate` panel. Once signed in, they open a waiting room (Firestore-backed), share its link/QR, watch participants join live, then close registration to distribute players into pods of 3–5 (never 1v1 or bare pairs), randomize pod assignments, and run a round timer.
- [unirse.html](unirse.html) — join page ("Unirme"): three-step, Kahoot-style flow. Step 1 validates the room code against Firestore (exists, and — for a first-time joiner — `estado === 'abierto'`) before showing anything else; only once that passes does step 2 reveal the name field and write the participant. Step 3 (`watchRoom`/`renderRoomState`) opens a live `onSnapshot` on the room doc: while `pods` isn't set yet it shows a waiting message, and once the organizer closes registration it shows the participant's own pod (opponent names, tagged "Tú" on themselves) plus a live round timer once the organizer starts one (`renderTimerDisplay`, synced from `torneos/{code}.timer` — see the timer section below). A returning participant (code already in `localStorage`) skips straight to step 3 even if the room is now `cerrado` — that's how they check their pod after closing. A code from the QR/link (`?code=`) auto-runs step 1 on load. This ordering is intentional — don't collapse it back into a single form.
- [firebase-config.js](firebase-config.js) — Firebase project config (`firebaseConfig` object), imported by both `crear-torneo.html` and `unirse.html`. Ships with placeholder values (`apiKey: "TU_API_KEY"`) — both pages detect the placeholder and disable the room/join flow with an explicit warning instead of failing silently. A real project must be created in the Firebase console (see comments in the file) and its config pasted in; this is a manual, per-deployment step that can't be automated from here.
- [firestore.rules.txt](firestore.rules.txt) — Firestore security rules to paste into the Firebase console. Not deployed automatically (no Firebase CLI/build step in this repo) — copy-paste is the intended workflow.

There is no build system, package.json, linter, or test suite. To work on this, open the HTML files directly in a browser (or serve the directory with any static file server) — there's nothing to compile. Note that `crear-torneo.html` and `unirse.html` use `<script type="module">` for the Firebase imports, so opening them via `file://` may block ES module loading/CORS in some browsers — prefer serving over `http://localhost`.

- [iniciar-servidor.bat](iniciar-servidor.bat) — Windows launcher for manual testing on a real phone: auto-detects the machine's local IPv4 address, serves the repo on it at port 3001 via `npx serve`, prints the organizer/join/deck-builder URLs to enter on a phone (or scan via the in-app QR), and opens the organizer page automatically. Requires the phone to be on the same Wi-Fi/LAN — `localhost` URLs won't work from a phone.
- [serve.json](serve.json) — config for `npx serve`. `"cleanUrls": false` stops `serve`'s default 301-redirect from `/unirse.html?code=XXXX` to `/unirse`, which used to **silently drop the query string** and break the QR/link auto-fill flow. Disabling `cleanUrls` also disables `serve`'s built-in extensionless→`.html` resolution, so `"rewrites"` explicitly maps `/crear-torneo`, `/unirse`, `/modulo-armar-mazo` and `/index` back to their `.html` files (a stale browser-history entry or a hand-typed URL without `.html` would otherwise 404). Keep both blocks in sync if pages are renamed.

## Architecture notes

Each page is self-contained: styles in a `<style>` block, markup, and logic in a single inline `<script>` IIFE at the bottom. There is no shared JS/CSS file between pages — common visual language (dark theme, gold accent `#C9A227`/`#c9a227`, card-based panels) is duplicated per file rather than factored out. Keep that in mind when making cross-cutting visual changes: they need to be applied in each file individually.

### crear-torneo.html — auth gate, live waiting room + pod distribution

Firebase app/Firestore/Auth are initialized once at top level (`if (firebaseReady()) { ... }`), not lazily inside a button handler like the pre-auth version did — `onAuthStateChanged` has to be listening before the user does anything, since it's what decides whether `authGate` or `step1` is visible. `currentUser` is a module-level variable updated by that listener; every Firestore-writing handler downstream (`createRoomBtn`, `addManualBtn`, `closeRoomBtn`, `reshuffleBtn`) assumes `db`/`auth` are already set, since none of them can be reached while `step1` is hidden pre-login.

`authGate` has two tab-toggled forms (`showLoginTab`/`showRegisterTab`, `.tab-btn.active`). Login is plain `signInWithEmailAndPassword`. Register additionally requires picking an account type (`.account-type-btn`, `data-type="individual"|"tienda"`) before it'll submit — picking `tienda` reveals a required `direccion` field (`tiendaFields`). On success, `createUserWithEmailAndPassword` is immediately followed by `setDoc` on `usuarios/{uid}` with `{ tipo, email, direccion?, creado }`; if that second write ever needs to become resilient to partial failure (auth account created but profile doc missing), that's a known gap — currently a failure there just surfaces as a generic error with the auth account already existing. `traducirErrorAuth` maps Firebase Auth error codes to Spanish messages; extend that map rather than showing raw `err.code` if new auth flows are added. `logoutBtn` (`signOut`) also tears down the room UI state — unsubscribes any live listener, resets `roomCode`, and hides step 3/timer — since the next login could be a different organizer.

Joining a tournament (`unirse.html`) still requires no account at all — the gate only applies to *creating* one. This is enforced both in the UI (step1 hidden pre-login) and in [firestore.rules.txt](firestore.rules.txt) (`torneos` `create`/`update` require `request.auth != null` and ownership via `organizadorUid`; `participantes` `create` still has no auth requirement).

Data model in Firestore: `torneos/{code}` (fields `estado`: `'abierto'|'cerrado'`, `creado`, `organizadorUid`) with a `participantes` subcollection (fields `nombre`, `unidoEn`). `code` is a random 5-char string generated client-side (`generateCode`), not a Firestore auto-ID — it's what goes in the shareable link/QR (`unirse.html?code=...`) and what players type in manually if they don't scan.

Flow: `createRoomBtn` creates the room doc and opens an `onSnapshot` listener (ordered by `unidoEn`) that live-renders the roster and enables "cerrar inscripciones" once there are ≥3 names. `unirse.html` looks up the room doc by code, checks `estado === 'abierto'`, and `addDoc`s a participant — it never reads or writes anything else, and can't edit/remove entries (see [firestore.rules.txt](firestore.rules.txt)). The organizer can also add walk-in names manually into the same subcollection (`addManualBtn`) so mixed remote/in-person signup merges into one list. `localStorage` on the join page (`ld_joined_{code}`) just prevents a participant from double-submitting on refresh — it's not auth.

Closing registration (`closeRoomBtn`) snapshots the current roster into `lastRosterNames`, flips `estado` to `'cerrado'` (so late joiners get rejected by `unirse.html` and by the security rules), and unsubscribes the listener — the pod step no longer reacts to Firestore.

All three Firestore-writing handlers (`createRoomBtn`, `addManualBtn`, `closeRoomBtn`) wrap their `await` calls in try/catch, disable-then-re-enable their trigger button, and surface failures via `countWarning`. This isn't optional error-handling boilerplate — without it, a transient Firestore hiccup (the WebChannel `Listen`/`Write` streams do occasionally error and reconnect, confirmed via the console during testing) leaves the button permanently disabled with no code/roster ever rendered and zero feedback, which reads as "the app is broken" rather than "retry". Keep this pattern if you add more Firestore calls here.

`distributePods(n)` chooses the number of pods by minimizing `|n/pods - 4|` over the valid range `[ceil(n/5), floor(n/3)]`, then spreads the remainder round-robin so pod sizes differ by at most 1. This is what guarantees pods of 3–5 with no leftover 1v1s/pairs. `lastRosterNames` is shuffled and redistributed across those pod *sizes* (`shuffle` + `renderResultPods`), both on close and on "volver a sortear" (`buildPodsArray`).

Pod assignments are also written to Firestore (`torneos/{code}.pods`) on both close and reshuffle, so participants can see their own pod from `unirse.html` in real time — **not just render locally on the organizer's screen**. `pods` is `{ jugadores: string[] }[]`, i.e. an array of maps each holding a plain name array — **not** `string[][]`: Firestore rejects arrays nested directly inside arrays, which is why each pod is wrapped in a one-key map. `unirse.html` matches by exact name string against this same collection (no participant IDs), which is a known limitation shared with the rest of the no-login design: duplicate names in one room are ambiguous.

**Round timer sync** (`torneos/{code}.timer`, shape `{ totalSeconds, remainingSeconds, endsAtMillis, running }`): rather than decrementing a counter every second and writing that to Firestore continuously, the timer stores an *anchor* — `endsAtMillis`, the epoch-ms instant it hits zero — and every device (organizer and each participant independently) recomputes `remaining` locally every second as `endsAtMillis - Date.now()` while `running`, or reads `remainingSeconds` directly while paused. This is why `persistTimer()` in `crear-torneo.html` only fires on the four control actions (Aplicar/Iniciar/Pausar/Reiniciar) — never on a tick — and why `unirse.html`'s `renderTimerDisplay()` runs off a local `setInterval` reading the last-received `lastTimerState`, not a new Firestore read each second. This design means the countdown doesn't drift or stall if a tab is backgrounded/throttled (a plain `setInterval` decrement would), and it keeps Firestore writes rare. It relies on each device's system clock being roughly correct — no server-clock reconciliation is done, which is an accepted tradeoff for a casual round timer, not a competition-grade one. The timer only appears in `unirse.html` once `data.timer` exists on the room doc, which only happens after the organizer's first interaction with the timer controls — a participant never sees a phantom default timer.

### modulo-armar-mazo.html — decklist parsing and validation

State machine driven by a `state` object (`tab`, `commanderCards`, `deckCards`, `resolved`, `manualCommanderKeys`) inside the IIFE.

- Two text parsers: `parseMoxfieldFormat` (expects `Commander` / `Deck` section headers, exported directly from Moxfield) and `parsePlaintextFormat` (no headers; assumes the *last* line is the commander). Both funnel through `parseCardLine`, which extracts qty/name/set/collector-number via regex.
- Card validation calls the public Scryfall collection endpoint (`POST https://api.scryfall.com/cards/collection`) in batches of 75 to resolve card names to real cards (art, type line, legality-shaped checks). No API key needed; failures are treated as "unresolved" rather than fatal.
- The "Enlace de Moxfield" tab currently cannot succeed: Moxfield's API is not authorized for this app, so `handleLinkImport` deliberately throws after the fetch and shows a fallback prompting the user to paste text instead. Don't try to "fix" this without first getting real Moxfield API access — the failure is expected/documented behavior, not a bug.
- Commander detection is automatic (first/last card depending on parser) but overridable: `manualCommanderKeys` lets the user star any card in the full list as the commander instead.

## Language

All UI copy, labels, hint text, comments, and communication with the user must be written in **neutral (Latin American) Spanish** — never Argentine or any other regional dialect. In practice:

- Use `tú` conjugations for the second person singular (`tienes`, `quieres`, `elige`, `ingresa`), never `vos`/voseo (`tenés`, `querés`, `elegí`, `ingresá`).
- Avoid Argentine-specific vocabulary and slang (e.g. `acá` → `aquí`, `link` → `enlace`, `celular` is fine as it's widely understood, but region-specific idioms should be avoided in favor of terms understood across all Spanish-speaking countries).
- When adding or editing any user-facing string in these HTML files (or writing chat responses to the user), review it against this rule before finalizing — it's easy to slip back into voseo out of habit.
